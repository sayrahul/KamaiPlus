## 2. The two real bugs — read this section first if you're debugging a recurrence

These are the two bugs actually responsible for essentially every "product disappeared" / "logout wiped my data" report across the whole session. If either symptom resurfaces, re-read this section before assuming something new broke.

### 2a. Business type could silently change, and the app treats it as a hard partition key

**Where:** `lib/views/settings/store_profile_screen.dart` (fixed in `0f75008`).

Every product and category in this app is tagged with a `business_type` string (`grocery` / `pharmacy` / `clothing` / `hardware` / `restaurant` — see §2c for why those exact five strings matter), and `LocalDatabase.getAllProducts()` / `getAllCategories()` filter **strictly** by whatever the currently active type is. The Settings screen used to let a merchant change this via a dropdown, and on every Save — even one that never touched that dropdown — it unconditionally called `seedVerticalStarterData(_selectedBusinessType)` and `BusinessVerticals.updateActiveBusinessType(...)`. If `_selectedBusinessType` ever drifted from the store's real, already-populated type (a stray dropdown tap, or the profile's `businessType` field being empty on some load), the entire real catalog became invisible behind the new filter, and the app auto-seeded a fresh, empty starter catalog for whatever the (wrong) new type was — which reads exactly like "my products vanished and defaults came back."

**Fix:** business type is now locked at signup, permanently, for the life of the account. `store_profile_screen.dart`'s Settings screen shows it as a read-only field with a lock icon and the caption "Locked at signup — use a different account to run a different type of store." `signup_store_screen.dart` remains the *only* place a business type is ever assigned. Two defense-in-depth layers were also added directly in `local_database.dart`:
- `getAllProducts()`'s auto-seed-a-starter-catalog path now only fires if the business has **zero products of any kind** (a genuinely brand-new store) — never on top of an already-populated one, regardless of which vertical is being queried.
- `saveStoreProfile()` refuses to let an incoming empty `business_type` blank out an already-saved non-empty one.

**Do not build any UI, anywhere in this codebase, that lets an existing account change its business type.** A store that genuinely needs a different vertical signs up with a different account.

### 2b. Firestore sync never round-tripped `business_type` at all — the live, ongoing corruption source

**Where:** `lib/services/firestore_sync_service.dart` (fixed in `ab08da4`).

This is the bigger one, and it was **still actively happening** even after 2a's fix, which is why the same symptoms kept reproducing on a second, completely independent test device with a fresh account. It was found by pulling that device's actual on-device SQLite file directly (see §5, "How this was actually diagnosed") and finding every single product — all 36 rows, no exceptions — tagged `business_type='grocery'` on a store whose real type was `clothing`.

`pushProductToCloud()` built its Firestore payload from roughly 25 named fields, and `business_type` was never one of them — checked directly in the payload literal, genuinely absent. Symmetrically, both `initialCloudRestore()`'s product-restore loop and the live products-collection listener inside `_startLiveCloudListeners()` reconstruct a `ProductModel(...)` from a cloud document on every restore or change, and neither ever read a `business_type` field back — because it was never there to read. `ProductModel`'s constructor default for `businessType` is the literal string `'grocery'` (`lib/models/models.dart:188`). The result: **every single cloud round-trip silently reset a product's vertical tag to `'grocery'`** — including a local device's own write being echoed straight back to it by Firestore's live snapshot listener, which happens within moments even for changes the same device just made.

This is the complete explanation for the whole symptom set:
- *Add a product, watch it vanish* — tagged correctly, pushed to cloud, echoed back stripped of `business_type`, gone from every vertical-filtered view within about a second.
- *Edit a quantity/price, product disappears* — identical mechanism.
- *Logout → login wipes everything* — `initialCloudRestore()` re-pulls the entire catalog on every login, and since no cloud doc had ever carried `business_type`, the whole catalog reset at once, all together — which is exactly what "everything got wiped" feels like from the outside.

The same bug also hard-coded `'is_favorite': false` in the push payload regardless of a product's real favorite state, so favoriting something would silently un-favorite itself on the next sync.

**Fix, in both directions:**
- `pushProductToCloud()` now writes `'business_type': product.businessType` and the real `'is_favorite': product.isFavorite`.
- `initialCloudRestore()` and the live products listener both now read `business_type` back from the cloud doc — falling back to `BusinessVerticals.activeBusinessTypeNotifier.value` (the store's own locked type from §2a) rather than `ProductModel`'s `'grocery'` default, since every product doc pushed *before* this fix still lacks the field and always will unless re-pushed.
- `LocalDatabase`'s repair logic (see §2c) was extracted into a public `repairMistaggedProducts()` and is now called immediately after every `initialCloudRestore()`, not only during a schema upgrade — a brand-new device inheriting already-corrupted pre-fix cloud docs still gets cleaned up.

**If you ever add a new code path that reconstructs a `ProductModel` from Firestore data, grep for `ProductModel(` first and confirm `businessType:` is explicitly set.** This is the second time this exact shape of bug has hit this codebase (see §2c for the first).

### 2c. Legacy on-device data corruption from an earlier, already-fixed bug

**Where:** `lib/core/database/local_database.dart`, `_migrateToV6` / `repairMistaggedProducts()` (fixed in `88e33ee`, extended in `ab08da4`).

Before 2b's live bug was found, the *first* pulled SQLite dump (a different device, a Pharmacy store) showed duplicate products under the same name with different `business_type` tags — e.g. three copies of "Dolo 650 Paracetamol" tagged `grocery` (two of them with real stock) alongside one correctly-tagged `pharmacy` copy. This traced to an **already-fixed** bug in `lib/views/products/quick_stock_update_modal.dart`: an older version of `_saveInward`/`_saveAdjustment` rebuilt a product's row from a fresh `ProductModel(...)` instead of `copyWith(...)` on every quick stock/price update, which (same root cause as §2b) silently reset `businessType` to the `'grocery'` default. That code is correct today (verified `copyWith` is used in both methods) — but fixing the code never repaired the data damage it had already done on any device that hit the bug before the fix shipped.

**Fix — `repairMistaggedProducts()`, a two-pass repair:**
1. **Seed-catalog pass:** every product name in `kDefaultProductsByVertical` is unique to exactly one vertical, so a row whose name matches a seed name but whose `business_type` doesn't match that seed's real vertical is unambiguously mistagged. If a correctly-tagged sibling with the same name already exists, the mistagged row is a pure duplicate and gets deleted; if it's the only copy, it's re-tagged in place — **never deleted, so stock data is never lost.**
2. **Store-wide sweep:** since business type is now permanently locked (§2a), a store can only ever have one true vertical for its whole lifetime — so a broader second pass reads the store's own locked type from `store_profile` and applies the identical dedupe-or-retag logic to *every* mistagged product, including a merchant's own manually-typed custom products (not just seed-catalog matches, which the first pass can't reach). This is what caught real "test"/"qwerty"-style manual entries found on the corrupted device.

Runs automatically via the schema `onUpgrade` path (bumped to version 6) for any device with pre-existing data, **and** is called directly after every `initialCloudRestore()` (§2b) so a brand-new device — whose database is created fresh at the latest schema version and therefore never goes through `onUpgrade` — still gets cleaned up if it inherits corrupted pre-fix cloud docs.

**Regression tests:** `test/mistagged_product_repair_test.dart` (new, 3 tests) manually constructs a v5-schema database with the exact corruption pattern (a duplicate-with-sibling case, an only-copy case, and a should-not-touch custom-product case) and asserts the post-upgrade state. `test/vertical_product_leak_test.dart`'s pre-existing test that asserted "switching business type auto-seeds a new catalog" was **rewritten** — that assertion described the bug this session fixed, not correct behavior — into "a business that already has products is never phantom-seeded," plus a new test confirming a genuinely empty store still seeds correctly.

**The 5 canonical business-type ids in this codebase, exactly:** `grocery`, `pharmacy`, `clothing`, `hardware`, `restaurant` (see `signup_store_screen.dart`'s `businessTypeId` values — the only place these are ever assigned). A related, smaller bug was found and fixed in the same investigation: `store_profile_screen.dart`'s own locked-display dropdown list used the keys `'apparel'`/`'electronics'` instead of `'clothing'`/`'hardware'`, so the read-only display silently showed "Grocery / Kirana" for a Clothing store even though the underlying stored value was correct the whole time. **Always check any new business-type string switch/map against `signup_store_screen.dart`'s real ids — several files in this codebase have independently invented near-but-not-quite-matching strings for the same five verticals.**

## 3. How the two devices' corrupted data was actually found

Not by guessing from source code alone — by pulling each test device's real SQLite database file directly and querying it with `sqlite3`. This is worth documenting because it's a repeatable, effective technique and because getting it wrong silently corrupts the read:

- **`adb pull` and `adb exec-out ... > file` both corrupt binary files when run through this session's Git Bash on Windows** — every `0x0A` byte in the binary stream gets expanded to `0x0D 0x0A` (CRLF), which breaks a SQLite file's header and body silently (produces a file that *looks* plausible in size but fails `sqlite3`'s integrity checks or, worse, loads with corrupted content).
- **The reliable method:** `adb shell "run-as com.kamaiplus.pos cat databases/<file> | base64"`, captured as text (base64 is immune to newline translation since it's pure ASCII), then decoded on the host with a small Python script. Confirmed byte-for-byte correct by comparing decoded file size against the `ls -la` size on-device.
- **If the database is in WAL mode** (check for a `-wal` file with `.length > 0` next to the main `.db` file), you must pull the `.db`, `-wal`, and `-shm` files together into the same local directory with matching names — `sqlite3` will only merge uncommitted WAL content automatically if all three files are present together on open. Reading just the main `.db` file gives you a stale, incomplete view.
- Force-stop the app first (`adb shell am force-stop <package>`) to get a consistent snapshot before pulling.

This technique surfaced §2c on the first device (a Pharmacy store, `kamaiplus_ZnqHTPUW1iagbCvdRJOMNM1ZSrQ2.db`) and §2b on the second (a fresh Clothing/Apparel store called "my Footstore," Redmi 6 device, `kamaiplus_GcmNKeELCsaod3c860Xp5lruU5n1.db`).

### 4b. Permanent delete — `88e33ee`

Explicitly requested as *distinct* from 4a — the user was asked directly whether "delete" should mean reversible disable or genuine permanent erasure, and confirmed the latter for this second action: same email should be able to sign up fresh from zero afterward.

- **Required a real Firestore rules fix**, not just an admin-console change: `firestore.rules`' `businesses/{businessId}/products|categories|customers|sales|inward_orders` subcollections (and the `{allChildren=**}` catch-all) previously granted write access to `isBusinessOwner()` only — even though the parent `businesses/{businessId}` document itself already allowed `isBusinessOwner() || isAdmin()`. This admin feature was the first thing to actually need admin write access on those subcollections, exposing a real, pre-existing gap in the rules that's now closed the same way the parent doc already was. - UI: `merchant_detail_screen.dart`'s `_PermanentDeleteDialog` requires typing the merchant's exact store name to enable the confirm button — a stronger pattern than a plain Yes/No, deliberately, for an irreversible action on real merchant data.
- **Explicitly documented limitation, in both the code comment and the confirmation dialog text shown to the admin:** this only reaches Firestore. If the same physical device still has the store's data cached locally (this app is offline-first SQLite), it stays there until that device's app data is cleared or the app is reinstalled — no admin action can reach into a merchant's own phone.
- A red "DISABLED" badge (for 4a) also now shows next to a merchant's name in the Merchants list/table/card view, not just on the detail page, so a disabled account doesn't stay hidden behind a click-through.

## 5. UI consistency pass — notifications to the top, cards shrunk twice

### 5a. Every notification now renders from the top of the screen — `c7e7d3c` + `71bba81`

Flutter's `SnackBar` is architecturally bottom-anchored to its `Scaffold` — there is no theme property or `SnackBarBehavior` value that repositions it to the top. This app already had a top-capable alternative, `InAppNotification` (`lib/views/common/in_app_notification.dart`, an `Overlay`-based widget), fixed earlier in the session to slide in from the top instead of the bottom. Getting *every* notification onto that behavior required migrating every remaining `ScaffoldMessenger.of(context).showSnackBar(...)` call site to it — **123 occurrences across 41 files**, found via a full-codebase search.

This was done as an explicit, individually-verified migration rather than a bulk find-and-replace, specifically because the user had repeatedly and explicitly worried about a large mechanical change silently breaking working code:
- Each call site was read and converted by hand to the semantically equivalent `InAppNotification.success()/.error()/.info()/.show()` call, preserving whatever custom icon, color, action button, or duration the original `SnackBar` had.
- `flutter analyze` was run on the specific file immediately after each edit.
- Full-repo `flutter analyze` + the complete `flutter test` suite were re-run at roughly four checkpoints across the whole migration, not only once at the end.
- Split into two commits (`c7e7d3c` for the ~73 highest-traffic screens — POS billing, checkout, products, khata, login, transactions, customers, dashboard, menu, inventory, cash register, GST reports; `71bba81` for the remaining ~50 — purchases, AI bill/menu scanning and review sheets, backup/restore, printer settings, invoice themes, Pro membership, barcode studio, low-stock reorder, UPI standee, and the two service classes — `AppPrinterService`, `ShareTargetService` — that call this from outside a widget's own `build()`, holding a `BuildContext` via a navigator key instead) so the work was never in an all-or-nothing, unverified state.
- A full-codebase search for `ScaffoldMessenger.of(context).showSnackBar` after the migration returns **zero matches**.

**`InAppNotification`'s API, for future call sites:** `.success(message, {context, actionLabel, onAction})`, `.error(message, {context})`, `.info(message, {context, actionLabel, onAction})` cover most cases. `.show(context:, message:, type:, customIcon:, customColor:, actionLabel:, onAction:, duration:)` is the full form — use it for anything needing a custom icon/color/duration, or the `warning` type (there is no `.warning()` convenience method). **`.success()`/`.error()`/`.info()` do not accept a `duration` parameter.** Do not use `ScaffoldMessenger.of(context).showSnackBar(...)` anywhere in this codebase going forward.

## 9. Suggested QA checklist for the user

1. Add a new product → confirm it appears immediately in both the product list and the POS billing grid.
2. Edit a product's quantity or price → confirm it does not disappear.
3. Log out, then log back in → confirm products, stock quantities, sales history, and customers are all still there.
4. Settings → Store Profile → confirm business type shows locked/read-only with the correct vertical (not defaulting to Grocery).
5. Trigger any action that used to show a message (save, delete, error) → confirm the notification now slides in from the **top**, not the bottom.
6. Products screen → toggle to grid view → confirm cards are visibly smaller than before.
7. Admin Console → Merchants → open a test merchant → **Disable** → confirm their Android app signs out within a few seconds; **Re-enable** → confirm they can log back in with data intact.
8. Admin Console → **Permanently delete** a genuine test-only merchant (not a real one) → confirm the type-to-confirm safeguard works and the merchant's data is gone from the cloud afterward.
